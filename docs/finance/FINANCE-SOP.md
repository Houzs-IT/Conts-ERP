- 版本：草稿 v1，2026-10-14
- 负责人：chew（财务）
- 状态：业务流程已与财务确认；标「待确认」的部分还没定（第 12 节）。系统做在哪里、分期上线见第 14 节。

## 1. 范围

整间公司（The Conts）只有一个财务模块，同时管两边的业务：

| 业务 | 说明 |
|---|---|
| Rental | 短租管理：业主、unit、订单、业主结算 |
| Supply chain / 装修 | 销售订单、采购、装修项目 |

财务人员只用**一个入口**处理两边的收款和付款，不用在两边之间切换。

手机与电脑的分工：
- 财务功能（核对、付款、对账、报表等）只在电脑上，不开放手机。
- 手机只用于提交：现场员工在手机上提交零用金使用、维修报告等，跟现在提交维修一样。

包括：付款、收款、生意以外的收付款、零用金、总账与科目表（COA）、银行对账、月结、报表、e-Invoice、SST。

## 2. 基础资料（由财务维护）

| 资料 | 内容 |
|---|---|
| 科目表（COA） | 用公司自己的科目表（现在 AutoCount 里那份）。系统的自动入账规则对应到这份科目表 |
| 费用类别表 | 员工看得懂的类别（清洁、水电、维修……），每个类别对应一个会计科目；可以标记「日常开销」（内部项目的预算不管日常开销） |
| 收款人名单 | 所有会收到公司钱的人：供应商、承包商、业主、员工、董事、其他人，含银行名称和账号。供应商部分就是 engine 现有的供应商名单（采购在用的那份），业主资料来自 Property OS，员工银行资料由 HR 提供。新增的要财务核对后才能付款；谁可以新增、修改：财务之后提供权限表 |
| 顾客（Debtor）、供应商（Creditor） | 每个顾客、供应商一笔资料，挂在一个 debtor / creditor control 下面，详见 2.1 |
| 公司银行账户 | 一家公司、多个银行账户（Maybank、Hong Leong），付款和收款都要选账户 |
| 部门 | Rental、Supply chain。每笔记录都标明属于哪个部门 |
| 公司费用分摊比例 | Rental / Supply chain，目前 50% / 50%，可以修改 |
| 项目费用上限 % | 全公司默认 70%，个别项目可以另外设定 |
| 装修分期收款模板 | 默认 10% / 50% / 35% / 5%，个别项目可以调整 |
| 发票付款期限 | 装修发票开出后 7 天到期（默认），个别项目可以另外设定 |
| 长租交租日 | 每月 7 日（默认），个别合约可以另外设定 |
| 维修项目表 | 每项的成本价；加价 % 默认 30%，可以按维修类别、个别项目另外设定 |
| 维修门槛金额 | 公司默认 RM 200，每个业主可以另外设定 |
| 取消费进业主结算单 | 开关，默认关（不算） |
| 装修：收到 50% 前开采购单 | 开关，默认只标红提醒；可以改成挡住 |
| 财政年度 | FYE 8 月（9 月 1 日到隔年 8 月 31 日） |
| 权限 | 谁可以确认业主同意、批准额外额度、拒绝申请、付款等，按用户和职位（position）设定。系统目前只有按角色设定，要加职位 |
| HOD | 到时由财务在用户设定里指定（目前对应 manager 角色） |

以上所有默认值和设定，财务都可以在系统设置里自己修改（maintain），不用改程序。

### 2.1 顾客（Debtor）和供应商（Creditor）（财务确认，2026-10-22）

- **Control**：每个顾客挂在一个 debtor control 下面，以后可以再加 control。按顾客类型分：
  - Rental 的顾客：新开 303-0000 RENTAL CUSTOMER（AutoCount 科目表没有，导入后在 ERP 加）。300-0000 以前混了别的东西，不再放新的 rental 顾客。303 是给 Airbnb 出租用的：收到钱就算 sales，方便按月 cut-off。Rental 的单从 Property OS 来，一过来就自动进 303；Property OS 还没和 ERP 接通，所以**暂时不用**，等接通时再做（财务确认，2026-10-24）；
  - 装修顾客：301-0000 RENOVATION CUSTOMER；
  - 自家装修（inhouse reno）顾客：302-0000 INHOUSE RENOVATION CUSTOMER。两种装修分开，因为毛利、销售员、买的货都不同。
  - **怎么分辨两种装修**（财务确认，2026-10-24）：项目有一栏「类型」——装修 / inhouse 装修。默认跟报价单的品牌：**The Conts → inhouse 装修（302）**，**Dream Crafter → 装修（301）**。在项目里改过的，以项目为准；报价转成销售订单（合约）之后就不再改。以后再加「绑定 user」（某个员工开的单默认某个类型），到时再定 user 和品牌哪个优先。
  - **一位顾客两种装修**（财务确认，2026-10-24）：**每种类型各开一个户口**。例如 MS LEE 先签 Dream Crafter 的装修 → 301-M001，后来又签 The Conts 的 inhouse 装修 → 另开 302-M00x。两笔分开看，毛利也分得清楚；同一种类型的新合约继续用原来的户口。一般的销售订单（不是装修）也算一种，挂在 300-0000，所以同一个人最多可能有三个代码。
  - **换 control**：顾客在 Debtors 页面换，供应商在供应商页面换；要有过账权限，先问一次确认。还欠钱的不能换，先在原来的 control 结清；已结清的旧记录留在原来的 control，代码不变。
- **维护**：财务可以维护每个顾客（debtor maintenance），像 AutoCount 一样看到「某个 control 下面的顾客」。
- **自动开顾客**：新订单来了，新顾客自动开一个 debtor，挂在对应的 control 下面。
- **代码**：control 的前三码 + 名字的第一个字母 + 流水号，例如 HOOKKA → 301-H001；个人顾客（MR / MS）用 M → 301-M001。流水号**不限位数**：至少三位，M999 之后是 M1000。
- **名称**：顾客、供应商、科目（包括项目子户口）的名称以后都可以改，不影响代码和已入的账。
- **代码在哪里看到**：顾客名单、顾客明细账里看得到就行，发票上印不印都可以。系统内部每张发票、每笔收款都要知道是哪个顾客的。
- **顾客明细账（debtor ledger）**：每个顾客看得到欠款、所有往来（合约、发票、收款、退款）和余额。
- **供应商同理**：一样有 control（400-0000 Trade creditors、405-0000 Other creditors），一样的代码规则和明细账。
- **科目表**：AutoCount 科目表里每个顾客、供应商的户口（SDR / SCR）**不当作会计科目**导入，导入成顾客和供应商名单，挂在各自的 control 下面。会计科目只到 control 为止。

## 3. 付款

### 3.1 应付款的来源

| 来源 | 谁录入 / 提交 | 何时产生应付 |
|---|---|---|
| 付款申请：报销、部门付款、订金 / 预付 | 办公室员工和主管（现场员工的费用由主管代提） | 提交后 |
| 供应商发票 | 采购 | 录入后 |
| 承包商请款 | 运营 | 维修工作完成、填好欠承包商的金额后 |
| Rental 账单（水电、清洁等） | 财务或运营 | 录入后 |
| 业主付款 | 系统自动 | 业主结算单发出后 |

### 3.2 付款申请要填的资料

**付款申请的类型**

| 类型 | 意思 | 收款人 |
|---|---|---|
| 报销 | 自己先垫了钱，申请还给自己 | 自动带出申请人自己 |
| 付款 | 付钱给供应商、承包商或其他人 | 从收款人名单选 |
| 订金 / 预付 | 发票还没来，先付一部分 | 从收款人名单选；自动标「还欠正式发票」，发票来了提示抵扣 |

**要填的资料**

| 栏位 | 必填 | 说明 |
|---|---|---|
| 申请类型 | ✓ | 见上表 |
| 收款人 | ✓ | 从收款人名单选。不在名单里可以直接新增（待核对，财务核对后才能付款） |
| 金额 | ✓ | |
| 用途 | ✓ | 可拆成多行，每行：部门、归属、费用类别、金额、说明（见下面） |
| 单据 | ✓ | 发票、收据或报价单，可以拍照（OCR） |
| 还欠正式发票 | | 先凭报价单付款时勾选，之后要补正式发票 |
| 关联采购单 | | 装修项目付供应商时选，方便以后抵扣订金 |
| 承担方 | Rental 才有 | 业主、公司、租客、押金、保修（见 3.3） |
| 希望付款日期 | | 供应商的付款期限 |
| 备注 | | |

- 系统自动带出：申请人、申请人的部门、申请日期；项目额度或预算还剩多少（超出就不能提交）。

**用途的每一行**
- 部门：Rental / Supply chain / 公司共用。默认带出申请人的部门，可以改。费用算哪个部门看这里，不看申请人。
- 归属（可以不选）：
  - unit：Rental 的 unit。
  - 项目：客户项目或内部项目（见 3.4）。展示厅这类也是一个项目，它的日常开销（租金、水电）记在这个项目下，就算这个项目的开销。
  - 都不选：算那个部门的一般费用。
  - 业主的 unit 在做装修：选装修项目，不是选 unit。
- 公司共用：按公司费用分摊比例（默认 Rental 50% / Supply chain 50%），也可以选全部算一边。
- 费用类别：这笔是什么费用，对应会计科目。

**付款方式的默认**

| 情况 | 默认 | 不对时 |
|---|---|---|
| 申请人的部门有零用金 | 自己垫的钱从部门零用金还（见第 6 节），不能改成报销（2026-10-29） | 不适用 |
| 没有零用金，付给供应商 | 银行转账；读扫描发票上的银行和账号，对应收款人名单 | 让申请人自己选或改 |
| 没有零用金，报销给自己 | 银行转账，用申请人在名单里的银行资料 | 让申请人自己改 |

- 公司从哪个银行账户付（Maybank / Hong Leong），由财务付款时选。

**OCR（拍照自动读）**

| 栏位 | OCR |
|---|---|
| 收款人 | 自动：读单据上的名字，对应收款人名单 |
| 日期、单据号码、金额（含明细） | 自动 |
| 费用类别 | 建议：按这个供应商以前用的类别，要人确认 |
| unit / 项目 | 单据上有写就自动读，对应系统里现有的 unit 或项目（只能是现有的）；读到我们的采购单号码也能对应到项目；读不出来或对不上就手选 |
| 部门、说明、承担方 | 要人填 |

- OCR 读出来的全部要人确认才保存。

### 3.3 业主承担的费用（Rental）

- 由谁承担，由提出费用的一方（运营 / CS）决定，不是财务决定。
- 一次性的业主承担费用（例如维修、为 unit 添购东西）：必须先由**有权限的人确认业主已同意**（附证明，例如讯息截图），才能提交付款申请。维修低于该业主的门槛金额不用通知业主（见 3.11）。
- 合约里约定的例行费用（水电、清洁等）不用每次确认。
- 系统按该 unit 的合约自动计算：

| 合约类型 | 业主承担多少 |
|---|---|
| Profit share / management | 进业主结算单，从收入中扣除后再分成，业主实际按分成比例承担 |
| Package D（有保底） | 同上，但业主有保底收入 |
| GRR（保证租金，即 Package C：公司每月付业主固定租金） | 费用归公司。要业主承担时，自动产生一笔 O2（业主调整），从租金里全额扣 |
| Master lease | 费用归公司 |
| Long term | 从租金中扣 |

- 财务付款时看得到「业主承担 RM xx，已确认」，不需要另外操作。

### 3.4 项目额度（装修 / Supply chain）

跟项目有关的付款申请，必须在项目额度以内才能提交。

- **可用额度** = 客户**实际已付**的钱 × 项目费用上限 %（默认 70%，财务可以修改）
  - 只算财务核对过、确实进账的钱。开了发票但客户还没付的不算。
  - 客户刷卡：按客户付的金额算，刷卡手续费是公司费用，不扣项目额度。
- **已用额度** = 公司**实际已付出去**的钱 + 已提交但还没付的申请（预留）
  - 按实际付出的钱算，不按供应商发票金额算。
  - 申请提交时先预留额度；实际付款后以实付金额为准，多出的预留退回。
  - 申请被拒绝，预留的额度全部退回。
- 额度**整个项目共用，先到先得**。
- **超出额度时不能提交**，系统提示剩余额度和超出金额。申请人可以**申请额外额度**：
  - 由有权限的人批准（例如财务、HOD、老板），在权限表里设定
  - 可以加一个金额，也可以调高该项目的百分比
  - 额外额度加到整个项目上
- 零用金用在项目上也扣额度（见第 6 节）。
- **付款凭证要不要一定选项目**（财务确认，2026-10-26）：先不规定。付供应商发票的，系统按发票自动带出项目；其他的由开单的人自己选，没选项目就不扣任何项目的额度。以后会改成提交付款的人一定要选项目或部门。

**内部项目（公司自己出钱）**
- 例：公司自己出钱装修 Master lease / GRR 的 unit 来出租；展示厅（装修和日常开销都记在展示厅这个项目下）。
- 开项目时选：客户项目（卖给客户，有收入和客户分期）或内部项目（没有收入、没有客户分期）。
- 内部项目要选算哪个部门：出租用的 unit → Rental；展示厅 → Supply chain。金额大的装修可能要当资产分几年摊（折旧），问会计师。
- **内部项目用预算代替额度**：开项目时定一个预算，付款申请加起来不能超过预算；超出要申请追加预算（照额外额度的流程）。
- **日常开销不受预算限制**：租金、水电这类日常开销照付；只有一次性的费用（例如装修）受预算控制。哪些费用类别算日常开销，在费用类别表里标记（财务维护）。
- 谁可以定预算、批准追加：老板、HOD、开项目的人、财务，在权限表里设定。可以设成「开项目的人填，老板、HOD 或财务确认」，避免自己批准自己花钱（填权限表时决定）。

例子（项目额度 RM 7,000）：

| 动作 | 已预留 / 已付 | 剩余 |
|---|---|---|
| A 申请 RM 3,000 | 3,000 | 4,000 |
| B 申请 RM 2,500 | 5,500 | 1,500 |
| C 申请 RM 2,000 | 超出 RM 500，不能提交 | 1,500 |
| 财务拒绝 B | 3,000 | 4,000 |
| C 重新提交 RM 2,000 | 5,000 | 2,000 |

### 3.5 审核

- 不设多级审批。
- 申请提交后**自动进入待付款**。
- 财务检查：没问题就开付款凭证（PV）付款；有问题就**拒绝**，必须写原因。拒绝后退回申请人，预留的额度退回。
- 申请人随时看得到自己申请的状态：

```
已提交 → 待付款 → 部分已付 → 已付
           ↘ 已拒绝（附原因）
```

### 3.6 付款中心

- 所有待付款项都在一个地方，可以按来源、部门、收款人、到期日、银行账户筛选。
- 显示到期日，过期标红。
- 订金抵扣：收款人名下有已付的订金或预付款时，系统会提示，确认后只付差额。

### 3.7 付款

- **批量付款**：勾选多笔（可混合各种来源）→ 建立付款批次 → 导出银行批量转账文件（Maybank、Hong Leong 格式）→ 上传到网银转账 → 回来标记整批已付，个别失败的单独标记。
- **单笔付款**：直接记录一笔付款。
- 一笔应付款可以**分几次付**；一次付款可以**同时付几笔**（例如同一个供应商的几张发票）。系统记录每笔还剩多少没付。
- 每次付款记录：日期、银行账户、付款方式、银行参考号、转账凭证（可选）。

### 3.8 欠正式发票

- 先凭报价单或形式发票付款时，财务可以标记「还欠正式发票」。
- 系统有一个欠发票清单，持续追踪，正式发票上传后才算结清。
- 正式发票来了，抵扣已付的订金或预付款，只付差额。

### 3.9 付款之后

- 来源单据自动更新为「已付」或「部分已付」（发票、请款、业主结算单等）。
- 需要通知的人自动收到通知（例如业主收到付款通知）。
- 自动入账（见第 7 节）。

### 3.10 费用算哪个月（cut-off）

- **原则：费用算在发生的月份。** 例：10 月 28 日修好冷气，发票 11 月 3 日才到，12 月 5 日付款 → 算 10 月。
- **如果那个月的业主结算单已经定稿**，就算在**还没结账的最早月份**（通常是下个月）。系统自动放进去，同时保留实际发生日期作参考。
- 公司总账用同一个月份，总账和业主结算单每个月对得上。
- 维修：按报价向业主收费（报价 = 成本 + 加价，见 3.11），所以维修完成时就知道扣业主多少，可以在完成的那个月扣。承包商的发票什么时候到，只影响公司付款给承包商，不影响扣业主。
- 水电等账单：账单到了才知道金额，放进还没结账的最早月份。
- **水电账单在 Property OS 录入**（财务确认，2026-10-26），跟 unit、业主结算单放在一起。账单用 OCR 读：TNB 等账单常把户口号码（account no.）遮掉，所以要从账单上其他资料认出是哪个 unit（例如地址、电表号码）。财务会提供几个月的真实账单做样本，和一份水电付款清单（payment listing）。
- **水电账单跨过合约开始日（或结束日）：按天数拆**（财务确认，2026-10-28）。天数以**账单上印的期间**为准，不是录入时选的月份。
  - 合约开始前（或结束后）的天数：**业主全付**，在分成之后从业主的付款中全额扣，不参与分成。
  - 合约期间的天数：照 3.3 的合约类型算。分成单位（Package A / B / D）照分成两边承担；GRR（Package C）由公司付，不扣业主的固定租金。
  - 例：账单 RM 310，期间 15/08–14/09（31 天），合约 11/09 开始，分成 80/20 → 合约前 27 天 RM 270 业主全付；合约期间 4 天 RM 40 照分成，业主 RM 32，公司 RM 8。
  - 系统要先能存账单期间（手动输入或 OCR）才能自动这样拆，**还没做**。现在系统只存账单月份，整张账单由录入时选的承担方承担，不会拆。

### 3.11 维修（Rental，业主承担）

**维修项目表**
- 每个维修项目记：成本价（付给承包商的）、加价 %、给业主的价钱（系统自动算 = 成本 × (1 + 加价 %)）。
- 加价 % 默认 30%，可以按维修类别（例如水电、冷气、家具）和个别项目另外设定。
- 系统已有维修项目表，但目前只有给业主的价钱，要加上成本价和加价 %。

**流程**
1. 开维修单：选项目，系统自动带出给业主的报价。表里没有的项目，输入成本，系统按类别自动加价。
2. 业主确认：每个业主有自己的门槛金额（没设定的用公司默认值）。
   - 报价不超过门槛：直接做，不通知业主。
   - 超过门槛：系统自动发给业主确认，业主同意后才开工。（系统已有业主确认功能，目前要人手动发。）
3. 完成后：按报价从业主结算单扣（月份按 3.10）。付给承包商的实际金额另外记，走付款流程。
4. 实际成本比预计高、使报价低于「成本 + 加价 %」时：系统提醒 HOD（manager）和财务，由他们决定要不要向业主补收。补收后如果超过门槛，要业主再确认一次。
5. 记账：加价部分是公司的维修收入，总账单独记。

例子（默认加价 30%，默认门槛 RM 200）：

| 维修 | 成本 | 给业主的报价 | 通知业主 |
|---|---|---|---|
| 换水龙头 | RM 100 | RM 130 | 不用，直接做 |
| 修冷气 | RM 400 | RM 520 | 超过 RM 200，自动发给业主确认 |

## 4. 收款

### 4.1 Rental

- 应收金额由订单决定。财务的工作是**对账**，确认钱确实进来了。
- 收款来源：
  - OTA（Airbnb、Booking.com、Agoda）：平台扣掉佣金后付**净额**；没有另外的佣金发票。一笔进账可能对应多张订单；各平台付款时间不同。
  - 客人直接转账。
  - 客人刷卡的手续费不由财务处理。
- 对账时金额对不上：由财务确认后做调整（正常应该对得上）。

### 4.2 装修

- 每个项目默认分 4 期收款，个别项目可以调整（系统现有默认 30/30/35/5，要改成 10/50/35/5）：

| 期数 | 比例 | 何时收（系统自动开发票） | 收到后 |
|---|---|---|---|
| 1 | 10% | 出报价单时（设计订金） | ID 开始设计 |
| 2 | 50% | 客户确认设计，报价单转成订单（合约） | 开始采购 |
| 3 | 35% | 木工（carpentry）和固定装置（fixture）开工时 | — |
| 4 | 5% | 完工、客户检查没问题、交房 | — |

- 每一期在哪个时间点开发票，是模板里的设定，可以改（某阶段开始或某阶段完成）。
- 第 1 期在报价阶段就收，那时订单还没产生：系统要调整，报价转成订单时，已收的 10% 自动算作第 1 期已收。
- 还没收到 50% 就开采购单：做成开关，**默认只标红提醒，不挡**；以后可以改成挡住。付供应商的钱仍然受项目额度限制（3.4）。
- 设计做了、客户最后没签约：已收的 10% 每次由财务决定全退、退一部分或不退；没退的部分算设计费收入。
- 报价或合约金额改了（改价、VO）：少收或多收的差额，在下一期发票补齐。每一期 = 到这一期为止总共应收 − 已经开的发票。例：第一版报价 RM 100,000 收了 10% = RM 10,000，最后合约 RM 120,000 → 第 2 期 = 60% × 120,000 − 10,000 = RM 62,000（本期 RM 60,000 + 第 1 期少收的 RM 2,000），四期加起来刚好 RM 120,000。
- Salesperson 在系统更新收款 → **财务核对银行确实收到** → 才算「已收」，项目额度才增加。
- 追加工程（variation order）：金额先加进下一期一起收。以后可能改成可以另外补收。
- 客户刷卡：手续费记为公司费用。
- **付供应商 / 承包商**：采购单上不设付款分期。采购或项目团队按跟供应商的约定提交付款申请（订金、尾款等），财务照申请付款，受项目额度限制。

### 4.2.1 装修收入：按完工进度（方法 B）

**决定（财务，2026-10-20）：装修收入按完工进度算。** 开发票和收钱的方式完全不变（照 4.2 的分期），改变的只是收入记在哪个月。

- 完工进度 = 已经记账的成本 ÷ 预计总成本，由系统自动计算。
  - 已经记账的成本：财务在总账里记在这个项目的成本（记在发生的月份，见 3.10）。**跟付了多少钱无关**，供应商有付款期限（term）也不影响。
  - 预计总成本：一开始等于订单每一行的成本（预算），之后按下面「实际和预计有差」的规则更新。
- 每月底系统自动计算：累计收入 = 完工进度 × 合约金额；本月收入 = 累计收入 − 以前已经算的收入。

**合约整笔入账（财务确认，2026-10-22）**：合约成立时，整个合约金额就记进顾客的应收和预收款，账上看得到每个顾客合约还没收多少、还没转成收入多少。开发票、收钱、算收入是三件分开的事：开发票只是告诉顾客这一期要付多少，不入账。

**预收款按项目分户口**：预收款（Accrual of sales）按品牌分两个总户口（480-0000 Dreamcrafter、481-0000 The Conts），每个项目在下面有自己的子户口，合约成立时系统自动开，例如 481-S012 SKYLINE D-25-13。代码照顾客的规则（2.1）：总户口前三码 + 项目名称第一个字母 + 流水号，不限位数。试算表上每个项目一行；项目结束、余额为 0 后可以停用。另外有一张项目状态表（4.2.3）。

例（合约 RM 30,000，第 1 期 RM 9,000）：合约成立 → 应收 30,000、预收款 30,000；开第 1 期发票 → 不入账；顾客付 9,000 → 银行 ↑ 9,000、应收 ↓ 9,000（注明付哪张发票），应收余额 21,000 = 合约还没收的钱；收入照下面按完工进度每月底转。已开发票、到期还没收的钱看发票的账龄。

| 动作 | 什么时候 | 入账 |
|---|---|---|
| 合约成立 | 报价单转成订单（合约）时 | 应收账款 ↑，预收款 ↑，整个合约金额（还不算收入） |
| VO、改价 | 合约金额改的时候 | 应收账款和预收款按差额加或减 |
| 开发票给客户 | 每期的时间点 | 不入账（只是单据） |
| 客户付钱 | 财务核对后 | 银行 ↑，应收账款 ↓ |
| 成本记账（供应商发票、费用） | 记在发生的月份 | 装修成本 ↑，应付供应商 ↑ |
| 付供应商 | 付款中心付款，按供应商的付款期限 | 应付供应商 ↓，银行 ↓（不影响利润，也不影响完工进度） |
| 月底（系统自动） | 每月最后一天 | 按完工进度，把预收款转成装修收入 |

例子（合约 RM 100,000，预算成本 RM 65,000）：

| 月份 | 开发票并收到 | 本月成本 | 完工进度 | 本月收入 | 月底预收款余额 |
|---|---|---|---|---|---|
| 9 月 | 10,000 | 0 | 0% | 0 | 10,000 |
| 10 月 | 50,000 | 20,000 | 31% | 30,769 | 29,231 |
| 11 月 | 35,000 | 35,000 | 85% | 53,846 | 10,385 |
| 12 月 | 5,000 | 10,000 | 100% | 15,385 | 0 |

- 做得比收得快时（累计收入 > 已开发票），差额记为「未开票收入」，下一期开发票时冲掉。
- 付供应商订金不算成本（记为预付款），记账成费用才算成本，所以付订金不会让完工进度变高。

**实际和预计有差（财务确认，2026-10-20）**
- 追加工程（VO）可以加项目、减项目、换项目。合约金额和预计总成本都跟着 VO 变（详细见下面「VO」）。
- 实际成本超出预计（某张采购单或某笔费用超出预算）：系统提醒 HOD 和财务，由他们确认新的预计总成本（已花的 + 预计还要花的）。
- 预计总成本改了：月底按新数字重算，差额算在当月，不改以前的月份。
- 交房前完工进度最多算到 99%，交房才算 100%，剩下的收入一次算清。这样就算预计没有及时更新，收入也不会在完工前被算满。
- 实际成本比预计低：不改预计也不会出错，只是收入算得比较保守，省下的部分在交房时一次算进来。如果中途就确定省了（例如采购单比预算便宜），系统同样提醒 HOD 和财务，确认后调低预计总成本，省下的部分在当月算进来。

**VO（财务确认，2026-10-20）**
- 加项目：合约金额加上 VO 的售价，预计总成本加上 VO 的成本。
- 减项目：合约金额减少。预计总成本要看那个项目进行到哪里：
  - 还没下单：直接减。
  - 已下单、还没收货：系统标记那张采购单要改单或取消，取消了才减。
  - 已经收货、成本已记账：成本减不了。退货给供应商（供应商开贷项通知单冲回成本），或转去别的项目或仓库，或认损失，由 HOD 和财务决定。
- 换项目：等于减旧的、加新的，按上面两条处理。
- 合约净减少：后面几期少收；如果已经收超过新的合约金额，开贷项通知单（退款或抵扣）。
- 每次 VO 后，月底按新的合约金额和预计总成本重算收入，差额算在当月。
- 预计会亏本（预计总成本 > 合约金额）：系统标红，按会计师意见处理（一般要马上把预计的亏损记下来）。
- 例（超支）：11 月发现总成本会是 RM 75,000，不是 RM 65,000。11 月进度 = 55,000 ÷ 75,000 = 73%（不是 85%），11 月收入 RM 42,564（不是 RM 53,846）；10 月不改；12 月交房再算 RM 26,667。项目毛利从 RM 35,000 变成 RM 25,000。
- 例（省钱）：总成本只用了 RM 60,000。不用改预计，12 月交房时进度算 100%，12 月收入 RM 15,385、成本 RM 5,000，项目毛利 RM 40,000。
- 没签约的 10%：留在预收款；财务决定不退的部分转成设计费收入，退的部分从预收款退。

### 4.2.2 结案和保修（财务确认，2026-10-20）

- 结案检查：以下都完成才算结案，没完成的在项目上标红：
  - 四期发票都开了，钱都收齐
  - 供应商的付款申请都付了，包括保留款
  - 楼管已退装修押金
  - 预收款和未开票收入都归零
- 项目盈亏表（每个项目一张）：预计成本、已下单、已记账成本、已付、已开票、已收、收入（按进度）、毛利（预计和实际）。
- 保修期：交房后的维修投诉变成 service case；维修费用算在发生的月份，标记属于哪个项目，并标为「交房后额外开销」。项目已经 100% 完工，不再改收入。
- **额外开销列表**：列出所有交房后的额外开销（项目、日期、内容、金额、供应商、对应的 service case），可以按项目、月份筛选。项目盈亏表也单独列出这部分，看得到扣掉额外开销后的毛利。

### 4.2.3 项目状态表（财务确认，2026-10-23）

每个装修项目一行，看工程进度、收钱进度、实际开销。栏位用栏位选择器（跟销售订单列表一样）：财务自己挑要看的栏位、排顺序，存成默认。

| 类别 | 栏位 |
|---|---|
| 项目资料 | 项目、顾客（代码和名称）、销售员、品牌（Dreamcrafter / The Conts）、类型（装修 / 自家装修）、目前阶段、预计交房日、有没有延误 |
| 金额 | 合约金额、VO、合约总额（合约 + VO） |
| 收钱 | 已收、Outstanding（合约总额 − 已收）、收钱 %（已收 ÷ 合约总额）、下一期收款（哪一期、金额、何时该开发票） |
| 收钱 gap | 每一期之间隔几天（第 1→2 期、第 2→3 期、第 3→4 期），两套：按收钱日期算、按开发票日期算 |
| 收入 | 已转 Sales、还没转（这个项目的预收款余额）、完工 %（成本进度，4.2.1） |
| 开销 | 预计总成本、Cost spent（已记账的成本）、已下单还没记成本（已开采购单、供应商发票还没来）、预计还要花、欠供应商多少；超支标红 |
| 毛利 | 预计 GP% =（合约总额 − 预计总成本）÷ 合约总额；到目前为止 GP% =（已转 Sales − Cost spent）÷ 已转 Sales |
| 额度 | 项目额度（3.4）已用、剩下 |
| 提醒 | 完工 % 比收钱 % 高很多（做在钱前面）标红 |

### 4.3 入账方式

- **收入记全额，手续费另外记费用。**
  - 例：客人付 RM 500，Airbnb 扣 RM 75，实收 RM 425 → 收入 RM 500，平台手续费 RM 75，银行 RM 425。
  - 刷卡同理。
- 业主结算单**照旧用净额**（按业主的 Excel 格式，不改）。算出来业主分到的钱一样。

### 4.4 退款

| 退款类型 | 谁发起 | 怎么处理 |
|---|---|---|
| Rental：OTA 订单的客人 | OTA 平台 | 平台退给客人，再从下一笔付给公司的钱里扣。财务对账时核对扣款，不另外付款 |
| Rental：直接订房的客人 | 运营 / CS | 提交退款申请 → 付款中心 → 财务付款。不能超过客人已付的金额 |
| 装修客户（取消、多付等） | Salesperson | 开贷项通知单（credit note）→ 提交退款申请 → 财务付款 |
| 供应商退钱（退货、多付等） | 采购 | 供应商开贷项通知单。退回的钱记为一笔收款，或直接抵扣下一张发票 |

- 退款申请跟其他付款申请一样进入付款中心，财务有问题可以拒绝。
- 装修退款会减少项目「实际已收」，可用额度跟着减少。如果项目已用超过新的额度，系统标记提醒财务（已付出去的钱拿不回来）。

### 4.5 发票和正式收据

发票和正式收据由系统自动开，不需要人手动开。

**Rental 直接订房**
- 发票：入住当天，如果订单没有取消，系统自动开。入住前改日期或金额都不用作废发票，因为还没开。
- 客人入住前就需要发票（例如公司报销），可以手动提前开。
- 延住：另开一张发票。提早退房要退钱：开贷项通知单。
- 正式收据：客人每付一笔钱开一张，**财务对账确认收到后**才自动开。

**Rental OTA 订单**（OTA = Online Travel Agency，即 Airbnb、Booking.com、Agoda 等订房平台）
- 平台自己开给客人，公司不开。客人另外直接付给公司的部分，照直接订房处理。

**装修**
- 每一期在它的时间点到了时自动开发票（见 4.2）：第 1 期出报价单时；第 2 期报价转成订单时；第 3 期木工和固定装置开工时；第 4 期交房时。
- 第 3、4 期由项目团队在系统里标记「开工」或「交房」触发。标记前系统先提示：「这会自动开第 N 期发票 RM xx 给客户」，避免误点。
- 正式收据：财务核对收到钱后自动开。

**e-Invoice**
- 发票按 LHDN 规定提交。已验证的 e-Invoice 只能在规定时间内取消（目前 72 小时），之后用贷项通知单修正。细节问会计师。

### 4.6 跨月 cut-off（Rental）

原则：**sales 按客人实际住的日子算，跟钱什么时候到无关。**

- **收入按晚分到各月。** 例：10 月 30 日入住、11 月 2 日退房，3 晚 RM 600 → 10 月 RM 400（2 晚），11 月 RM 200（1 晚）。跟业主结算单的算法一样。
- **手续费跟收入一样按晚分。** 例：Airbnb 扣 RM 90 → 10 月 RM 60，11 月 RM 30。这样总账每个月的「收入 − 手续费」跟业主结算单的净额完全对得上。
- **钱早到、还没住**：先记为预收款（还不算 sales），客人住了才按晚转成收入。
- **住了、钱还没到**：sales 照算，同时记应收（平台或客人欠公司的钱），钱到了冲掉。
- 预收款和应收**每个月底由系统自动处理**，财务不用手动做 cut-off 分录。报表可以随时看：
  - 预收款清单：付了钱但还没住的订单
  - 应收清单：住了但还没收到钱的订单
- **取消费**：算在**取消当天的月份**，**单独记录**为取消费收入，不算住宿收入。直接订房的取消费和 OTA 订单取消后平台付给公司的钱，都记为取消费收入，报表可以按来源（直接订房 / Airbnb / Booking.com / Agoda）分开看。
  - 例：10 月 1 日订 11 月 5–8 日（RM 600），10 月 20 日取消，公司留下 RM 300 → 10 月的取消费收入 RM 300。
  - 要不要进业主结算单：做成开关，默认不算（目前系统也不算，被取消的订单完全不进结算单）。
- 取消费金额：OTA 订单由平台的取消政策决定。直接订房不设系统计算的政策：由 CS 决定要不要退给客人，要退就提交退款申请（见 4.4）。

### 4.7 长租租金

- 每份长租合约设定：租金**付给公司**，或**直接付给业主**。
- **付给公司**：
  - 每月自动产生一笔应收租金，租客交了就对账（跟其他收款一样）。
  - 所有合约：公司按合约租金定期付给业主（扣管理费和业主承担的费用），不管租客当月有没有交。
  - 租客欠租由公司追。要用押金抵欠租时，**由财务触发**，系统不会自动扣。
- **直接付给业主**：公司不经手租金。每月系统自动**开发票给业主**：管理费 + 业主承担的费用。
  - 业主转账付款：对账，跟其他收款一样。
  - 同一个业主还有其他 unit 的钱在公司（业主结算单要付给他）：可以 **contra 对冲**。在业主结算单加一笔业主调整（O2）扣掉这张发票，发票记为已付（对冲）。不够扣的部分，业主另外转账。
  - 系统在产生业主结算单时提示可以对冲，财务确认后执行。
  - 例：业主陈先生的长租 unit，租客把 RM 2,000 直接转给他；这个月管理费 RM 200 + 维修 RM 150 → 发票 RM 350 给陈先生。他另一间短租 unit 这个月要付他 RM 1,800 → 结算单扣 RM 350（对冲），实付 RM 1,450。

### 4.8 押金

原则：**押金不是收入，也不是费用。** 收来的押金是公司欠别人的钱（以后要退）；付出去的押金是别人欠公司的钱（以后会拿回来）。系统单独追踪每笔押金的余额，直到退还或抵扣。

- 短租不收押金。

| 押金 | 何时 | 处理 |
|---|---|---|
| 长租租客押金（含水电押金） | 租约开始时收，结束时退 | 不管租金付给公司还是直接付给业主，押金都由公司收，记为公司欠租客的钱。租约结束：CS / 运营检查后提交退押金申请，押金 − 欠租 − 损坏 = 退给租客，走付款中心。扣下的欠租冲掉应收租金（租金直接付给业主的合约，扣下的欠租付给业主）；扣下的损坏费用用来付维修 |
| 装修押金（付给楼管） | 开工前付，交房后退回 | 走付款申请（挂在项目下），记为楼管欠公司的钱。**不算项目额度，但一定要追回**：交房后系统持续提醒，直到楼管退回。楼管扣掉的部分算项目成本 |
| Master lease 押金（付给业主） | 合约开始时付，结束时退回 | 走付款申请，记为业主欠公司的钱。合约结束业主退回时冲掉；被扣的部分算公司费用 |

- 用押金抵欠租或损坏：由财务触发，系统不会自动扣。
- **押金清单**：每笔押金的余额和状态（持有中 / 已退 / 部分扣除）。该退未退的提醒财务，例如交房后 30 天楼管还没退。

### 4.9 催款

- 适用：装修分期款、长租租金、公司开给业主的管理费发票（已 contra 对冲的不提醒）。
- 到期日（默认值，可以在设置里修改）：
  - 装修发票：开出后 7 天。个别项目可以另外设定。
  - 长租租金：每月 7 日。个别合约可以另外设定。
- **只提醒内部**，不自动发给客户，由负责的人自己跟客户说。
- **过了到期日还没付才提醒**，到期前不提醒：

| 什么时候 | 提醒谁 |
|---|---|
| 过了到期日还没付（例如 7 日到期，8 日提醒） | 负责的人（装修：salesperson；长租和业主：CS）+ 财务 |
| 之后每 7 天 | 同上，一直到收到钱 |

- 负责的人记录「收到钱」就停止提醒；财务核对发现钱没进账，提醒恢复。
- 过期的款项在应收账龄报表标红。

## 5. 生意以外的收付款

走同一套收款 / 付款流程，只是记到不同科目：

| 类型 | 收 / 付 | 科目 |
|---|---|---|
| 股东注资 | 收 | 股本 |

**公司银行账户之间转账**

- 对账时两边银行月结单都配对到同一笔转账。转账手续费（如有）另外记为银行手续费。

**薪水**

- 以后可能改成系统计算和发放。
- 按员工所属部门分配：Rental 员工算 Rental，Supply chain 员工算 Supply chain。
- 两边都做的员工（例如老板、财务）：照 HR 提供的分配记录（HR 给的时候大多已经分好）。

## 6. 零用金

- **按部门管理**（2026-10-29 改，原本是按人管理）。一个部门一份，财务指定一个保管人保管，余额按每份计算。
- **每份零用金有自己的会计科目**（财务确认，2026-10-29）。科目表里已经每份一个户口，用保管人的名字命名，例如装修部 → 315-0100 PETTY CASH - ALEX (RENO)，维修部 → 315-0101 PETTY CASH - AMIN。开零用金时选好户口；收据从这个户口扣（借：费用，贷：这个户口），补回也补进这个户口（借：这个户口，贷：银行）。一个户口只能给一份零用金用。户口一旦记过账就不能换，要换就用分录转余额，另开一份。
- 一个人最多保管一份（财务确认，2026-10-28）。算哪个部门（Rental / Supply chain / 公司共用）看每一行选的部门。
- **两边都可以提交**（财务确认，2026-10-28）。零用金使用、报销和付款申请，在 Property OS 和 Supply chain 系统都可以提交，不限制在哪边；两边看到的是同一份资料。财务的核对、付款、补回都在 Finance 一个地方做。
- **定额制。** 财务按每份设定金额（每份可以不同，随时可以调整）。补回后回到定额。
- 办公室员工、主管、现场员工（清洁员、技术员）都可以持有。

**使用**
- 员工每用一次就提交一次收据：日期、收据照片（OCR 读金额），以及用途（unit / 项目 / 公司、类别），可拆成多行。
- 收据一提交就当作保管人已经付了，马上从余额扣除（财务确认，2026-10-29）。保管人什么时候把现金给员工，是他们之间的事，系统不记。
- 部门决定要填什么：装修部门的收据大多要选项目（只在 Supply chain 系统用）；用在项目上的，算进项目额度，超出只标记、不拦住。
- 用在项目上的，同时扣项目额度。因为钱已经花出去，超出额度时不能拦住，只能标记超出、提醒财务。
- **一个提交画面**（财务确认，2026-10-28）：先选这笔是什么。
  - **维修**：选自己的维修单，unit 和部门自动带出。在维修单上传自己的收据（文件类型选「My purchase」）就自动生成，不用选谁付、不用上传两次（2026-10-29 改：原本要选"我的零用金"或"报销给我"）。这笔是维修单的成本，业主照报价扣（3.11），**不会从这笔再扣业主**。
  - **Claim**：一般开销。
  - 金额用 OCR 从收据读出，**提交的人（包括现场员工）提交时看得到并确认**；读不出就自己填（财务确认，2026-10-29）。现场员工看得到自己收据的金额，但看不到零用金余额，也看不到维修单的报价和成本。
- 给 unit 买、要业主付、但不是维修的东西（例如热水壶）：第一版先不处理，照现在的做法由运营在 Property OS 录进业主结算单（财务确认，2026-10-29）。每个人看到哪几种，以后在用户设定里绑定。
- **按部门**（财务确认，2026-10-29）：**一个部门一份零用金**，由一个保管人保管（任何员工都可以，不一定是上司）。部门里的人提交的收据都从这份扣，保管人用现金还给他们。个别员工可以在设定里改成向别的部门的零用金 claim。部门没有零用金的，收据转给财务当 claim。有零用金的部门，收据一律从零用金扣，保管人**不能**转给财务；钱不够就申请补回（财务确认，2026-10-29）。
- **普通员工**在手机上看不到金额和余额（财务确认，2026-10-29）。
- **买货**（财务确认，2026-10-29）：
  - 维修零件进仓库，成本用加权平均，用了才算费用；拿货的规则要和管理层确认后再定。
  - Supply chain 的货一律开 PO，收到货或要付款时，按 PO 提交付款申请，不用零用金买。
- 现场员工在手机上记录和拍收据（属于提交，跟提交维修报告一样）。核对、补回等财务工作只在电脑上做。

**核对**
- 财务核对每笔使用的收据。
- 有问题可以拒绝，并写原因：持有人要补收据，否则这笔由持有人自己承担。

**清单**（财务确认，2026-10-28）
- 每个持有人一份零用金清单：定额、现在余额，和他提交的每一笔使用（日期、用途、unit / 项目、类别、金额、核对状态、收据照片）。
- 可以按月份筛选，可以导出 Excel。
- 另有总览：每个持有人的定额、余额、待核对金额、上次补回日期。

**补回**
- 每月固定补回一次；中间不够用时，持有人也可以申请补回。
- 余额低于一定比例时，系统提醒持有人。
- 补回金额是已核对的使用金额。
- **可以用超过定额**（财务确认，2026-10-28）：余额可以变负数，超出的是持有人自己先垫的钱，系统不会拦住。下一次补回时，已核对的全部补回给他，余额回到定额。补回走付款中心，付给持有人。

例子：财务分配 RM 500 给阿明（运营部）

| 动作 | 阿明的余额 |
|---|---|
| 分配 | 500 |
| 买清洁用品 RM 80，用在 unit A-01 | 420 |
| 买五金 RM 150，用在项目 P-012（扣项目额度） | 270 |
| 财务核对后补回 RM 230 | 500 |

### 7.1 上线和期初余额

- 现在公司的账在 **AutoCount**。目标：**2026 年 11 月**开始在 ERP 记账。
- 上线日是财政年度中间（FY 2026/27 从 9 月 1 日开始），所以期初余额要包括 9 月 1 日到上线前一天的损益，全年报表才完整。

  - 押金清单：收着的、付出去的
  - 董事往来余额、每份零用金的余额、应付给业主还没付的钱
- **不跟 AutoCount 并行**：11 月起直接在 ERP 做账，AutoCount 保留作历史资料查询。
- 因为没有并行对照，期初余额导入后要逐项核对一次：试算表总数、每个银行账户余额、应收应付清单、押金清单。

## 14. 系统做在哪里、分期上线

**决定（财务，2026-10-15）：公司总账用 engine（Supply chain 系统）现成的那套。**

- 理由：engine 已经有科目表、会计分录、试算表、损益表、资产负债表、银行对账（上传月结单自动配对）、月结锁账、应收应付账龄、付款凭证，科目编号也是 AutoCount 格式。导入科目表和期初余额就能开始记账，11 月可以开始用。
- 要加的：部门和 unit 维度（engine 的分录目前只能标项目）；Property OS 把 Rental 的交易自动送进 engine 总账；两边侧边栏都有 Finance 入口。
- **对使用者只有一套**：一个 Finance 入口、一本总账（engine）。Rental 的业务（订单、业主结算、维修）留在 Property OS，钱的记录自动送进 engine 总账。
- **现况（2026-10-20 查过）**：engine 的会计页面（科目表、付款凭证、收款、银行对账、每日银行）在 Property OS 菜单里没有入口；Property OS 还有一套旧版的 Accounting（/accounting）和 Payment vouchers（/procurement/payment-vouchers），用旧版数据（pos），跟 engine 的发票对不上。第 1 期要加 engine 会计页面的入口，并关掉这两个旧版页面。
- 本地开发财务功能时，要同时跑 engine 和它的数据库（目前本地只跑 Property OS，Supply chain 显示的是旧版）。
- 改 engine：财务已和 Zaim 确认可以直接改（2026-10-15）。
- 上线：财务模块由财务（chew）自己处理，已和 Zaim 确认。需要向 Zaim 拿 staging 和正式数据库的连线资料、Cloudflare 权限（密钥用 USB 或密码管理器传，不在聊天或邮件里传）。
