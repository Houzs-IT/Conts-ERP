1 · Architecture position

The Conts is a branded extension of the existing Houzs and Hookka React foundation, not a new frontend. Reuse the application shell, routing, authentication, tables, forms, dialogs, icon library and data-fetching patterns exactly as they are. Apply The Conts identity through the theme token contract and compose property-management domain modules from shared primitives.

LayerRule for this project
FoundationOne agreed version set across the three products. Confirm the exact package stack before implementation; do not swap libraries for aesthetic reasons.
UI primitivesButton, Input, Select, Dialog, Table, Tabs, Badge, Toast. Never fork to change colour or radius.
Shared patternsAppShell, PageHeader, FilterBar, DataTable, FormSection, AuditTimeline. Extend through documented props and slots.
Brand themetokens.css under [data-theme="theconts"]. No hard-coded brand values inside shared components.
Domain modulesReservationCalendar, UnitReadiness, OwnerStatement, OperationsQueue. The Conts-specific until their API stabilises.

5.2 Operations today · /operations/today

A prioritised list, not a Kanban. The backend supplies riskRank and the SLA label so the order and countdown are authoritative. Each row shows unit, work, readiness, next guest time, SLA and exactly one action. Row edge colour repeats the SLA tone; the label always carries the meaning in words.

5.3 Reservation calendar · /reservations/calendar

Units as rows, dates as columns, unit names frozen during horizontal scroll. Channel and status are printed on every block, so Airbnb, Booking.com, Agoda, direct, maintenance block and owner stay remain distinguishable without colour. Dragging a block never saves silently.

  • Add booking → POST /api/reservations. A 409 returns the conflicting reservation: “Blocked. #A-12-03 already has Chen Y. on those dates.”
  • Drag a block → PATCH /api/reservations/:id/dates. Without confirm the API returns 428 and the dialog states the consequence: “Move Nadia Abdullah to 18–21 Sep? This updates the channel and notifies the guest.”
  • Block dates → a reservation with channel maintenance_block or owner_stay, excluded from occupancy and ADR.

5.4 Unit record · /properties/units/:unitId

Seven tabs: Overview, Reservations, Operations, Financials, Maintenance, Documents, Activity. Overview combines current guest, next check-in, readiness, open issues, owner and the monthly profit and loss. The Financials tab requires a finance-permitted role. Activity is the audit trail: actor, timestamp, before and after state, source.

Access codes are masked by default. Revealing one requires an operations or management role and writes an access.reveal audit entry.

5.5 Owner statements · /finance/statements

The gross-to-net chain is explicit and the three revenue definitions are never merged. A statement can only be sent once finalised; provisional rows show the state and disable sending with a reason.

5.6 Owner portal · /owner

Lower density, plain language, confidence and traceability first. Hierarchy: payout and status, then occupancy, ADR, bookings and rating, then the gross-to-net breakdown, then the trend, then property health, then documents. Every deduction carries a category, date, amount and reference. Provisional periods are labelled as such.

  • Download statement → GET /api/owner/statements/:id/pdf
  • Download per document row → GET /api/documents/:id/download
  • Approve quote on a waiting issue → POST /api/maintenance/issues/:id/approve, confirming: “Approve RM 890 for blackout curtains? The Conts will schedule the work and deduct the amount from your next statement.”

5.7 Field mobile · /field/today

Single column, 44 px minimum targets, readable in a car park. Shows address, access instruction, checklist, due time and a contact route. Financial data is never present in the response, not merely hidden.

  • Add photo → POST /api/tasks/:id/photos. At least one photo is required before a unit can be marked ready.
  • Mark ready → POST /api/tasks/:id/complete, confirming: “Mark #A-12-03 ready for guest? Next check-in is 15:00.” Sets unit readiness to Ready.
  • Report damage or missing item → POST /api/maintenance/issues, creating an open issue on that unit with photos.
  • Call operations → tel:+60174658868.
  • Offline queue shows Queued, Synced and Failed to sync as distinct states. Nothing reads as success before the server confirms.

6 · Table, filter and export behaviour

  • Rows 48 px standard, 40 px compact. Headers sticky, sentence case, with visible sort state.
  • Text left; money and comparable numbers right with a consistent currency label; status left, consistently.
  • Critical row actions are always visible — never hover-only, for touch and keyboard users.
  • Bulk actions appear after selection and state the selection count and scope.
  • Finance and audit tables use explicit pagination with a stated page size; very large operational lists may virtualise.
  • Every export prints applied filters, generated time and data scope.

8 · Accessibility and localisation

  • WCAG 2.2 AA for contrast, keyboard use, focus visibility, error identification and control names.
  • Focus ring 2 px with offset, gold on light surfaces and gold on dark; never removed.
  • Minimum touch target 44 × 44 px in field and owner experiences.
  • Status never depends on colour, placeholder text, icon or hover alone.
  • English first, architecture ready for Bahasa Malaysia and Simplified Chinese, with 30 percent text expansion headroom.
  • Timezone Asia/Kuala Lumpur, currency MYR shown as RM, compact dates as 16 Sep 2026, ranges always disambiguated.

10 · Notifications

Full trigger, timing and payload table in notifications.md. The frontend surfaces these under Communication, Automations; the backend owns delivery. Four constraints shape the UI:

  • Access codes are never sent earlier than two hours before check-in, and only once the unit is Ready.
  • Quiet hours 22:00 to 08:00 MYT for non-urgent guest and owner messages. Check-in risk and payout failure override.
  • A failed send is a visible state on the related record with a retry action, never a silent drop.
  • Every notification has a durable destination in the product — a toast is never the only record.
